# 백엔드 테스트 작성·변경 기준

공통 작성 관점과 Java/TypeScript 예시는 [코드·테스트 작성 가이드](../docs/CODE_STYLE.md)를 따른다.
이 문서는 Java의 TDD 기록·동시성·계층별 검증 기준을 보완한다.

fixture는 전제와 자원 정리, action은 행동, assertion은 관찰 결과의 검증을 맡는다.
Java와 TypeScript 모두 같은 책임 분리를 적용한다.
테스트 개수나 통과 여부뿐 아니라 행동·기대 결과와 변경 과정을 읽을 수 있어야 한다.

## TDD와 리팩터링 기록

새 동작 또는 버그 수정은 아래 순서를 따른다.

1. 작은 행동 하나의 입력·결과·실패 의미를 테스트로 먼저 작성한다.
2. 구현 전에 실행하고 의도한 이유로 실패하는지 확인한다. 설정 오류·컴파일 오류와 행동 assertion
   실패를 구분한다. RED 로그와 변경 전 소스를 남긴다.
3. 그 행동을 만족하는 최소 구현을 하고 해당 테스트를 GREEN으로 만든다.
4. 테스트와 구현을 함께 리뷰·리팩터링하고 GREEN을 유지한다. 다음 행동은 다음 작은 순환으로 진행한다.
5. 관련 전체 Java 테스트를 실행한다. production 실행 경계에 영향이 있으면 최종 JAR로 공통 E2E를
   검증하고, 통과 범위와 미검증 범위를 따로 기록한다.

동작을 유지하는 리팩터링은 기존 GREEN → 구조 변경 → GREEN이 정상이다. 행동이 불분명하면 먼저
특성화 테스트를 작성한다. 변경 전에도 통과하는 특성화 테스트를 RED라고 부르거나, TDD처럼 보이도록
이력을 사후에 만들지 않는다. 기록에는 TDD / 특성화 / 동작 보존 리팩터링을 구분한다.

## 테스트 본문

- 준비 → 행동과 관찰값 수집 → 결과 검증을 빈 줄로 구분한다. 본문을 읽으면 어떤 행동의 어떤
  결과를 검사하는지 드러나야 한다. 중간 상태가 중요하면 행동 중 snapshot을 수집하고 마지막에 검증한다.
- 하나의 테스트는 하나의 행동 계약을 다룬다. 같은 실패가 상태·ID·lease를 모두 보존해야 한다면
  여러 assertion은 함께 둘 수 있다. 무관한 기능을 하나의 긴 시나리오에 넣지 않는다.
- `welcome()`처럼 실제 입장을 일으키는 호출은 assert 안에 넣지 않는다. 행동 단계에서 결과를 받아둔다.
- 테스트마다 독립된 fixture를 만든다. 앞선 테스트 통과나 실행 순서에 의존하지 않는다.
  공통 준비를 재사용하되 공통 준비의 기능 검증을 각 테스트에서 반복하지 않는다.
- 테스트 이름은 조건과 관찰 가능한 결과를 설명한다. 생성자에서 실패한 테스트를 `restore` 실행
  실패라고 이름 붙이는 등 실제 검증한 경계를 부풀리지 않는다.

## Fixture / action / assertion

| 역할      | 기준                                                                                                                                                                 |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fixture   | `editableRoom()`, `emptyRoom()`, `restoredRoom()`처럼 준비 상태가 드러나는 이름. 자원 정리도 소유한다. 호출부에 boolean 모드나 숨은 기본 시나리오를 노출하지 않는다. |
| Action    | 업무 행동과 필요한 완료 대기를 표현한다. 테스트의 결과 assertion을 함께 수행하지 않는다.                                                                             |
| Assertion | 관찰된 결과를 검증한다. 중첩 record 경로나 전송 장치가 업무 의미를 가리면 의미 있는 검증 함수로 숨긴다.                                                              |

도메인의 `openTerminal()`처럼 이미 의미가 명확한 API나 간단한 AssertJ 검증은 그대로 사용한다.
모든 줄을 helper로 감싸거나 Java에 TypeScript의 파일 분할을 그대로 복제하지 않는다.
fixture 준비가 실패하면 명확한 예외로 중단하고 자원을 정리한다. 이것은 준비 기능을 테스트 본문에서
반복 검증하는 것과 다르다. 잘못된 fixture를 조용히 성공으로 취급하지 않는다.

파라미터화는 같은 행동·기대 결과에 대한 입력 변형에 사용한다. 본문에 setup용 lifecycle switch나
성공/실패별 assertion 분기를 늘리지 않는다. 이름 있는 사례와 fixture/provider가 준비를 맡는다.
공유되는 입력은 불변 값이어야 하며 테스트 사이에 살아 있는 Room이나 연결을 공유하지 않는다.

## 동시성·계층 경계

- 저장 gate/latch/제어 가능한 실행기로 경합 조건을 만들고 대기에는 제한 시간을 둔다.
  sleep이나 스레드 스케줄링 우연으로 순서를 추측하지 않는다.
- `Thread.State.WAITING`만으로 특정 방 lock을 기다린다고 단정할 수 없다. `RoomPersistenceTests`는
  대상 명령 큐와 종료 큐를 구별해 관찰하고 마지막에 상태·이벤트·종료 순서를 검증한다.
  접수 확인은 fixture 내부의 제한된 reflection에 의존한다. 이 white-box 의존성과 선택 이유는
  [동시성 테스트 정리](../docs/WORK_LOG.md#테스트-표현과-동시성-관찰)에 기록했다.
- domain/application 테스트는 업무 상태와 typed 결과를 검증한다. JSON 필드명·binary 형식은
  adapter와 공통 프로토콜 E2E에서 검증한다. 해당 계층의 테스트에서는 실제 wire 표현이 필요하다.
- 테스트 장치가 이벤트 순서·중복을 정렬하거나 제거해서 실제 결함을 가리지 않도록 한다.

## 2026-09-27 점검 결과

| 작업               | 실제 근거                                           | 분류                                                                                                 |
| ------------------ | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| P3v 저장 경계 통합 | 기존 테스트 통과 전후 비교                          | 동작 보존 리팩터링                                                                                   |
| P3w 명령 결과 분리 | 변경 전에도 통과하는 lease 대기 테스트 추가 후 변경 | 특성화 + 리팩터링                                                                                    |
| P3x host 불변식    | 새 6개 사례의 assertion 실패 후 구현·통과           | 실제 RED → GREEN. 다만 사례를 한 묶음으로 진행했으며 행동별 짧은 순환으로 더 작게 진행할 여지가 있음 |

이번 컨벤션 정리는 P3x의 lifecycle 준비를 provider로 옮기고 실제 거절 경계에 맞춰 테스트 이름을
수정했다. `RoomPersistenceTests`에는 `editableRoom()`을 명시하고 준비용 boolean 분기를 제거했다.
production 코드와 기존 행동 기대값은 변경하지 않는다. 이것도 새 기능 TDD가 아닌 테스트 리팩터링이다.

후속 P3y에서 긴 복합 시나리오를 세 계약으로 나누고 rename 행동과 저장 제목 assertion을 명명했다.
`awaitBlocked()`의 거짓 양성을 먼저 재현한 뒤 실제 대상 큐 관찰로 교체했다. 다른 긴 시나리오와
직접 상태 접근까지 일괄 정리한 것은 아니다. 이후 변경하는 테스트에도 같은 기준을 적용한다.

검증 기록은 `artifacts/migration-baseline/test-convention-review/`에 둔다. 실제 SQLite 재시작과 전체
브라우저 검증은 공통 Spring 프로세스 E2E 통과와 구별한다.

이번 테스트 리팩터링 후 Java 전체 277개가 실패/오류/건너뜀 없이 통과했다. production 코드는 바꾸지
않아 E2E를 재실행하지 않았다. 직전 P3x의 Spring JAR 공통 E2E 168개 통과는 별도 실행 기록이다.

후속 P4a는 [저장 생략 시나리오](../docs/WORK_LOG.md#테스트-표현과-동시성-관찰)를 행동별로 분리했다.
공통 계약만 파라미터화하고 다른 기대 결과는 별도 본문으로 읽히게 했다. 알림 비교는 준비 이후의
전체 알림을 보존하여 예상 밖 종류·중복도 검출한다.
