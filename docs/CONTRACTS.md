# 핵심 계약 → 코드 → 검증

대표 설계를 읽는 경로다. 모든 테스트의 목록이나 커버리지 수치가 아니다.

## 테스트를 읽는 기준

fixture는 해당 계약의 전제와 자원 정리를 소유한다. 본문에는 행동과 관찰 결과를 남긴다.
준비 단계에서 이미 확인한 lease 획득 등을 매번 제품 결과처럼 다시 검증하지 않는다.
시간·저장·송신 실패는 조건을 만드는 수단이며, 기대 결과는 상태·수신 순서·자원 수명으로 표현한다.

동일한 공통 E2E를 Node와 Spring에 실행하되, 서버 내부 구조가 같아야 한다고 요구하지 않는다.
저장 후 알림의 공통 순서와 수신자별 예외 처리의 차이는
[전달 실패 사례](PORTFOLIO.md#판단-2-저장-성공과-전달-성공을-구분한다)에서 구분한다.
Spring의 `PeerUnavailable` 오류 주입 결과를 Node의 동일한 보장으로 확대하지 않는다.
테스트 개수 증가와 새로운 보장 추가도 구별한다. 기존 구현에서 즉시 통과한 테스트 보강을
RED → GREEN 사례로 설명하지 않는다.
