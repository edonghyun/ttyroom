# TTYRoom 브레인스토밍

> 상태: 초기 제품 가설  
> 작성일: 2026-08-12

## 한 문장 가설

TTYRoom은 여러 개발자의 로컬·원격 터미널을 브라우저의 한 작업실로 모아 함께 보고, 나눠서 조작하고, 작업 맥락을 남기는 협업 도구다.

SSHX가 **내 터미널 하나를 공유하는 도구**라면, TTYRoom은 **팀의 여러 머신을 하나의 작업 공간으로 조립하는 도구**를 지향한다.

## 현재까지 합의된 방향

- 협업 화면은 브라우저에서 제공한다.
- 각 개발자 머신에는 UI 없는 Host Agent를 설치한다.
- Host Agent는 중앙 서버로 아웃바운드 연결을 유지한다.
- 하나의 Room에 여러 사용자와 여러 Host가 참여할 수 있다.
- Host마다 여러 Terminal을 열 수 있다.
- 기본 협업 방식은 터미널을 클릭해 입력권을 얻는 방식이다.
- 출력은 Room 참여자에게 계속 공유하고, 입력 권한만 통제한다.
- SSHX식 동시 입력도 선택 가능한 모드로 남길 수 있다.
- 터미널 렌더링은 검증된 xterm.js 계열을 우선 활용한다.
- 무한 캔버스보다 탭·분할·호스트 목록을 갖춘 작업 공간형 UI를 우선 검토한다.

## 제품 모델

```text
Team
└── Room: 결제 장애 대응
    ├── Host: 동현-MacBook
    │   ├── Terminal: backend
    │   └── Terminal: tests
    ├── Host: 민수-MacBook
    │   └── Terminal: frontend
    └── Host: staging-api-02
        └── Terminal: logs
```

핵심 식별 관계는 다음과 같다.

```text
RoomId + HostId + TerminalId
```

### 참여 역할

- **Participant**: Room에 참여한 사용자
- **Host Owner**: 자신의 머신을 Room에 제공한 사용자
- **Controller**: 특정 터미널의 입력권을 가진 사용자
- **Observer**: 터미널 출력을 보지만 입력하지 않는 사용자
- **Room Owner**: 참여자와 Room 정책을 관리하는 사용자

역할은 조직 전체의 고정 권한이 아니라 Room 또는 Terminal 단위로 달라질 수 있다.

## 가장 강한 사용 장면

### 1. 페어·몹 디버깅

백엔드와 프런트엔드 담당자가 각자의 머신을 같은 Room에 연결한다. 서로 다른 터미널을 병렬로 조작하고, 필요할 때 상대 터미널의 입력권을 받아 직접 확인한다.

### 2. 원격 도움과 온보딩

신규 팀원의 환경을 화면 공유로 설명하는 대신, 멘토가 같은 터미널을 관찰하고 명령을 제안하거나 입력권을 받아 문제를 해결한다.

### 3. 장애 대응

서버 로그, 로컬 재현, 데이터 조회, 배포 터미널을 한 Room에 모은다. 누가 어느 Host에서 무엇을 실행했는지 확인할 수 있다.

### 4. 작업 인계

실행한 명령, 종료 코드, 현재 경로, Git 브랜치와 메모를 남겨 다음 사용자가 작업을 이어받는다.

### 5. 사람과 코딩 에이전트의 공동 작업

Codex, Claude Code 등의 코딩 에이전트 터미널을 Room에 넣는다. 사용자는 여러 에이전트의 작업을 관찰하고 필요한 터미널을 클릭해 직접 개입한다.

이 사용 장면은 가능성이 크지만 초기 MVP에는 포함하지 않는다.

## 핵심 경험

```bash
ttyroom join payment-debug
```

Host Agent를 실행하면 내 머신이 기존 Room에 나타난다.

```text
Payment Debug
├── 동현-Mac
│   ├── backend       🔒 동현
│   └── tests         ○ available
├── 민수-Mac
│   └── frontend      🔒 민수
└── staging-api
    └── logs          👁 read-only
```

각 사용자는 서로 다른 터미널을 동시에 조작할 수 있다. 다른 사용자가 잡은 터미널은 계속 관찰할 수 있지만 자동으로 입력권을 빼앗지는 않는다.

## 터미널 입력권

입력권은 브라우저 포커스가 아니라 서버가 관리하는 터미널별 임대권이다.

```text
TerminalControlLease {
  room_id
  host_id
  terminal_id
  holder_user_id
  lease_id
  expires_at
}
```

입력 이벤트에는 현재 `lease_id`를 포함한다. 서버는 유효한 입력권 소유자의 입력만 Host Agent로 전달한다.

### 기본 동작 가설

1. 비어 있는 터미널을 클릭하면 입력권을 획득한다.
2. 다른 빈 터미널을 클릭하면 기존 입력권을 해제하고 새 입력권을 획득한다.
3. 다른 사용자가 잡은 터미널을 클릭하면 화면 포커스만 이동한다.
4. 입력이 필요하면 현재 소유자에게 제어권을 요청한다.
5. `Esc` 또는 잠금 버튼으로 입력권을 명시적으로 해제한다.
6. 연결이 끊기면 짧은 유예 후 입력권을 자동 해제한다.
7. 입력권이 해제돼도 해당 터미널에서 실행 중인 프로세스는 계속 동작한다.

### 터미널별 협업 모드

- **Exclusive**: 클릭한 한 사람만 입력할 수 있다. 기본 모드 후보.
- **Shared**: 허용된 여러 사용자가 SSHX처럼 동시에 입력할 수 있다.
- **Approval**: 참여자가 명령을 제안하고 Host Owner 또는 Controller가 승인한다.
- **Read-only**: 모든 원격 입력을 차단하고 출력만 공유한다.

## 브라우저 작업 공간

무한 캔버스보다 다음과 같은 IDE형 구조를 우선 검토한다.

```text
┌ Hosts ───────┬ Terminal Tabs / Split ────────┬ Participants ┐
│ 동현-Mac     │ backend │ tests               │ 동현 backend │
│ 민수-Mac     │                               │ 민수 frontend│
│ staging-02   │ $ npm run dev                │ 지훈 viewer  │
└──────────────┴───────────────────────────────┴──────────────┘
```

### 터미널 카드의 자동 맥락

```text
backend
동현-Mac · ~/projects/api · feature/payment
Node 24 · PID 18321 · 12ms
```

- Host와 소유자
- 현재 작업 디렉터리
- Git 저장소와 브랜치
- 현재 실행 중인 명령
- 입력권 소유자
- 연결 상태와 지연시간
- 마지막 활동 시각

## 입력 외 협업 기능 후보

- 특정 사용자가 보는 터미널을 따라가는 Follow 모드
- 참여자를 특정 터미널로 부르는 `모두 여기 보기`
- 바로 실행되지 않는 명령 제안
- 출력 구간 북마크와 코멘트
- 사용자별 포인터와 현재 보고 있는 터미널 표시
- 실행 명령, 실행자, 시간, 종료 코드 타임라인
- Host Owner가 모든 원격 입력을 차단하는 Kill Switch

명령 기록은 터미널 바이트 스트림을 추측해서 파싱하기보다 Host Agent의 셸 통합을 통해 의미 있는 이벤트로 수집하는 방식을 우선 검토한다.

## 시스템 구상

```text
개발자 브라우저 A ─┐
개발자 브라우저 B ─┼─ Control Plane / Room Gateway
개발자 브라우저 C ─┘              │
                    ┌─────────────┼─────────────┐
                 Mac A         Mac B         Server C
               Host Agent    Host Agent     Host Agent
                  ↖ outbound connections ↗
```

### 구성 요소의 책임

- **Browser App**: Room UI, 터미널 렌더링, 참여자 상태, 입력권 요청
- **Host Agent**: PTY 생성, 로컬 셸 실행, 암호화, 재접속
- **Control Plane**: 사용자 인증, Room과 Host 관리, 권한과 입력권 관리
- **Relay**: 브라우저와 Host Agent 사이의 실시간 메시지 전달
- **Tailscale**: 초기 사내용 배포의 네트워크 접근과 장치 신원 보조

터널 전송 방식은 제품의 상위 기능에 노출하지 않는다. 상위 모듈은 `Host 연결`, `Terminal 열기`, `입력권 획득`만 알고, WebSocket·gRPC·QUIC 또는 직접 연결 여부는 연결 모듈 내부에 숨긴다.

## Room 유형 가설

- **Quick Room**: 링크 또는 명령으로 즉시 만들고 작업 종료 후 사라진다.
- **Team Room**: 프로젝트에 귀속되며 Host, 권한, 작업 기록을 유지한다.

초기 제품은 SSHX의 가벼움을 유지하기 위해 Quick Room을 우선한다.

## 품질 기준

- 사용자는 Room에 들어온 뒤 누가 어떤 Terminal을 조작하는지 즉시 이해할 수 있어야 한다.
- 사용자의 의도 없이 다른 사람의 입력권을 빼앗아서는 안 된다.
- 네트워크 재연결이나 오래된 브라우저 입력이 현재 입력권을 우회해서는 안 된다.
- Host Agent 설치 이후 SSH 포트나 로컬 웹 포트를 외부에 열 필요가 없어야 한다.
- 느린 Terminal 하나가 다른 Host나 Terminal의 스트림을 막아서는 안 된다.
- 브라우저가 새로고침되어도 실행 중인 로컬 프로세스가 불필요하게 종료되어서는 안 된다.
- Host Owner는 언제든 자신의 머신에 대한 원격 입력을 차단할 수 있어야 한다.

## 주요 위험

### 제품 위험

- 화면 공유와 기존 SSH 도구보다 충분히 자주 사용할 이유가 있는가?
- 다중 Host가 실제 일상 협업에서 핵심인지, 데모에서만 매력적인지 검증이 필요하다.
- 클릭 입력권이 편리함보다 마찰을 더 만들 가능성이 있다.

### UX 위험

- 클릭이 화면 선택인지 입력권 획득인지 혼동될 수 있다.
- 여러 Terminal의 상태와 참여자가 많아지면 정보 밀도가 빠르게 증가한다.
- Shared 모드에서는 문자 단위 입력 충돌이 발생할 수 있다.

### 기술 위험

- IME, 복사·붙여넣기, 터미널 크기 변경과 재연결의 엣지 케이스가 많다.
- 다중 Host 환경에서 Terminal 식별과 메시지 라우팅을 처음부터 명확히 설계해야 한다.
- 터미널 출력의 backpressure와 느린 참여자 처리가 필요하다.
- E2E 암호화와 조직 감사 기능은 서로 충돌할 수 있다.

### 보안 위험

- 브라우저 입력은 실제 머신에서 임의 명령 실행으로 이어진다.
- 탈취된 Room 링크나 세션 토큰의 영향 범위를 제한해야 한다.
- 운영 서버 공유는 로컬 개발 머신 공유보다 강한 정책이 필요하다.
- 콘텐츠를 기록할 경우 비밀값과 개인정보가 저장될 수 있다.

2. 빈 Terminal 클릭 시 즉시 입력권을 얻는가, 명시적 Control 버튼을 누르는가?
3. 한 사용자가 동시에 여러 Terminal의 입력권을 가질 수 있는가?
4. Exclusive와 Shared 중 어느 것을 기본값으로 할 것인가?
5. Room 생성자는 자신의 Host만 공유하는가, 팀 Host도 호출할 수 있는가?
6. Host Agent가 기존 로컬 Terminal/tmux 세션에 붙을 수 있어야 하는가?

9. Tailscale 신원을 제품 사용자 신원으로 직접 사용할 것인가?
10. 브라우저 새로고침과 Agent 재시작 후 Room을 어떻게 복구할 것인가?

## 현재 추천

첫 검증 목표는 다음 경험 하나로 제한한다.

> 한 사용자가 Quick Room을 만들고, 두 명 이상의 개발자가 각자의 Host를 연결한 뒤, 브라우저에서 서로 다른 Terminal을 클릭해 동시에 작업할 수 있다.

이 경험이 기존 화면 공유, SSH, tmux 또는 SSHX보다 팀 협업에 실제로 편리한지 검증한 다음 기록·승인·영구 Room 기능을 확장한다.
